## ایده و هدف پروژه

ایده اولیه تکنوویا ساده بود: ساخت سیستمی که بتواند ۲۴ ساعته اخبار فناوری را از کانال‌های تلگرامی دریافت کند، اسپم‌ها و محتوای تکراری را کنار بگذارد، درباره موضوع در وب تحقیق کند، مقاله سئوشده و روان بنویسد، تصویر بسازد و در نهایت روی وب‌سایت و تلگرام منتشر کند؛ همه این‌ها بدون نیاز به دخالت انسانی.

برای پیاده‌سازی این روند، به‌جای یک خط لوله خطی ساده، از یک سیستم چندعاملی (Multi-Agent) با ۱۳ ایجنت هوش مصنوعی استفاده کردم که در ۵ ورک‌فلو متوالی روی LangGraph مدیریت می‌شوند.

## معماری ورک‌فلوها و چالش‌های فنی

### دریافت اخبار و تجمیع آلبوم‌ها (Telethon Listener)

ورودی سیستم، کلاینت Telethon است که پیام‌های کانال‌ها را شنود می‌کند. اولین چالش مربوط به آلبوم‌های تلگرام بود؛ تلگرام پست‌های چندرسانه‌ای را در قالب چند پیام مجزا اما با یک `grouped_id` یکسان می‌فرستد. اگر سیستم با دریافت اولین پیام شروع به پردازش می‌کرد، عکس‌های بعدی آلبوم از دست می‌رفتند. همچنین هایپرلینک‌های متنی تلگرام (`[متن](url)`) هنگام دریافت ساده، خراب می‌شدند.

برای حل این مشکل، یک مکانیزم Debounce دوثانیه‌ای اضافه کردم تا سیستم منتظر دریافت کامل تمام پارت‌های آلبوم بماند. سپس با ماژول `markdown.unparse` در تلتون، انکودینگ UTF-16 پیام‌ها را به مارک‌داون روان تبدیل کردم تا لینک‌ها بدون تغییر آفست حفظ شوند.

### ورک‌فلو ۱: فیلتر اسپم، تشخیص شباهت معنایی و دیتابیس برداری

![Processor Workflow](https://res.cloudinary.com/dwy6ves9w/image/upload/v1784972503/1_processor_workflow_tldqci.png)

پیام‌های ورودی ابتدا از فیلتر `deepseek-v4-pro` می‌گذرند تا آگهی‌های تبلیغاتی، استخدامی و اسپم‌ها حذف شوند.

برای تشخیص اخبار تکراری بر اساس مفهوم (نه فقط کلمات)، از مدل `gemini-embedding-2` (تولید بردار ۷۶۸ بعدی) و دیتابیس برداری TurboVec استفاده کردم. در پیاده‌سازی اولیه، لود کردن مستقیم ایندکس برداری داخل کدهای جنگو باعث شد مصرف RAM به ازای هر ورکر WSGI/ASGI به‌شدت بالا برود و سنکرون نگه‌داشتن دیتای جدید بین ورکرها سخت شود.

برای حل این مشکل، دیتابیس برداری را به یک میکرو‌سرویس مجزا روی FastAPI منتقل کردم. از آنجا که TurboVec امکان ذخیره متادیتای پیچیده را ندارد، شناسه جنگو (`django_id`) را به عنوان نگاشت در TurboVec قرار دادم. در سمت مقابل، درون PostgreSQL علاوه بر شناسه خارجی بردار، **خروجی باینری امبدینگ** را هم ذیل همان رکورد ذخیره کردم. این کار دو فایده داشت: ارتباط اتمیک بین دیتابیس سنتی و برداری برقرار شد و در صورت از دست رفتن ایندکس برداری، امکان بازسازی کامل آن از روی بایت‌های Postgres وجود دارد، بدون اینکه نیازی به کال مجدد API گوگل و صرف هزینه باشد.

تصمیم‌گیری برای اخبار تکراری بر اساس حد شباهت انجام می‌شود:
- شباهت زیر ۶۵٪: خبر جدید است و وارد چرخه می‌شود.
- شباهت بالای ۹۲٪: خبر قطعا تکراری است و بلافاصله رد می‌شود.
- بین ۶۵٪ تا ۹۲٪: محتوا به `deepseek-v4-flash` داده می‌شود تا تصمیم نهایی را بگیرد.

در بخش رسانه، تصاویر با Gemini Vision بررسی می‌شوند و اگر واترماک یا آیدی کانال رقیب داشته باشند، به `QwenImageEdit_Plus_NF4` ارسال می‌شوند. برای اینکه مدل المان‌های بومی رابط کاربری (مثل دکمه‌ها یا قیمت‌ها) را به اشتباه پاک نکند، پرامپت سیستم طوری تنظیم شد که المان‌های تعاملی UI دست‌نخورده بمانند و فقط واترماک‌های ناشر حذف شوند.

### ورک‌فلو ۲: تحقیق زنجیره‌ای و نگارش مقاله

![Writer Workflow](https://res.cloudinary.com/dwy6ves9w/image/upload/v1784972565/2_writer_workflow_nykfyz.png)

اجرای سرچ‌های همزمان و موازی معمولاً نتایج سطحی می‌داد و باعث توهم مدل (Hallucination) می‌شد. به همین دلیل، ایجنت تحقیق (`Researcher Node`) کوئری‌های ابزار Tavily را به‌صورت متوالی اجرا می‌کند؛ یعنی سرچ دوم بر پایه نتایج سرچ اول انجام می‌شود. برای جلوگیری از خطای تاریخی، تقویم زنده شمسی و میلادی به کانتکست اضافه شده و سقف ۳ سرچ در سطح کد پایتون اعمال شده تا گراف وارد لوپ بی‌نهایت نشود.

برای مدیریت محدودیت نرخ (Rate Limit) یا قطعی شبکه هنگام نگارش، یک زنجیره ۵ مرحله‌ای با تاخیر فزاینده پیاده‌سازی شده است:

$$\text{Gemini 3.5 Flash (Deep Thinking)} \longrightarrow \text{Gemini 3 Flash} \longrightarrow \text{Gemini 3.1 Flash Lite}$$

در بخش لحن، عبارت‌های کلیشه‌ای هوش مصنوعی فیلتر می‌شوند تا متن حالت مقاله تحلیلی به خود بگیرد. تصاویر موجود با فرمت `![alt](media_id:ID)` و تصاویر پیشنهادی جدید با `![custom_alt_farsi](suggestion_id:LOCAL_ID)` نشانه‌گذاری می‌شوند.

![SEO Workflow](https://res.cloudinary.com/dwy6ves9w/image/upload/v1784972592/3_seo_workflow_jfxybz.png)

### ورک‌فلو ۴: ساخت تصویر و مدیریت Race Condition

![Image Workflow](https://res.cloudinary.com/dwy6ves9w/image/upload/v1784972625/4_image_workflow_x4dbpt.png)

اگر خبر مربوط به شخص یا محصول واقعی باشد، تصویر از گوگل (Serper API) واکشی می‌شود و اگر مفهوم انتزاعی باشد با مدل `ZImageTurbo` تولید می‌شود. برای لایه جایگزین (Fallback)، به‌جای ساخت تصویر ساده با Pillow، ابتدا فراخوانی `Pollinations.ai` (مدل FLUX) برای تولید زنده عکس انجام می‌شود و در صورت خطای شبکه، یک تصویر استاتیک از Unsplash دانلود می‌گردد.

یکی از چالش‌های اصلی در این بخش Race Condition بود؛ تسک انتشار Celery گاهی چند میلی‌ثانیه قبل از Commit شدن کوئری‌های ذخیره تصویر بیدار می‌شد و پست بدون عکس منتشر می‌گردید. برای حل این مشکل، به‌روزرسانی‌های تصویر درون بلاک `with transaction.atomic()` با قفل `select_for_update()` قرار گرفت و فراخوانی تسک Celery به قلاب `transaction.on_commit` منتقل شد تا دقیقاً پس از تعهد نهایی داده‌ها روی هارددیسک اجرا شود.

### ورک‌فلو ۵: انتشار متمرکز در وب و تلگرام

![Publisher Workflow](https://res.cloudinary.com/dwy6ves9w/image/upload/v1784972660/5_publisher_workflow_gmhiys.png)

پس از تغییر وضعیت مقاله به `PUBLISHED` روی وب، بردار ۷۶۸ بعدی آن در مجموعه `contents` دیتابیس TurboVec ذخیره می‌شود تا در پیشنهاد مقالات مشابه و پیشگیری از تکرار در آینده استفاده شود.

در بخش ارسال به تلگرام، کلاینت ناهمگام Telethon با ورکر همگام Celery در محیط داکر قفل می‌کرد (`async_to_sync` باعث Deadlock می‌شد). برای حل این بن‌بست، درون متد ارسال یک ایونت لوپ جدید (`asyncio.new_event_loop()`) ساخته شد، اجرا در `asyncio.wait_for` با مهلت ۶۰ ثانیه محدود گردید و لوپ در بلاک `finally` بسته شد.

در نهایت لینک مقاله جای‌گذاری شده، برچسب‌ها به هشتگ تبدیل می‌شوند و پیام همراه آلبوم رسانه‌ها به کانال `@teknovia_ir` ارسال می‌شود.

## معماری فرانت‌اند، نحوه ارتباط با بک‌اند و شبکه CDN

فرانت‌اند تکنوویا با **Astro 7**، **SolidJS** و **Tailwind CSS v4** توسعه یافته است. هدف اصلی این بخش، رسیدن به بیشترین سرعت بارگذاری (Lighthouse 100) و سئوی کامل، در کنار کاهش بار سرور در ترافیک بالا بوده است.

```
[ کاربر ]
   │
   ▼
[ Cloudflare CDN Edge ]  ──(در صورت وجود کش s-maxage)──► [ پاسخ آنی به کاربر ]
   │
   │ (در صورت عدم وجود کش / Cache Miss)
   ▼
[ Nginx Reverse Proxy ]
   │
   ├──► [ Astro 7 Node Server ] (پورت 4321)
   │        │
   │        ├──(فراخوانی درون‌شبکه‌ای داکر)──► [ Django REST API ] (دریافت مقالات و دسته‌ها)
   │        └──(فراخوانی درون‌شبکه‌ای داکر)──► [ FastAPI TurboVec ] (پیشنهاد مقالات مشابه)
   │
   └──► [ Django Static / Media Files ] (فایل‌های استاتیک و عکس‌ها)
```

### ۱. ساختار رندرینگ و معماری جزایر (Astro 7 + SolidJS)

صفحات اصلی و مقالات به‌صورت Server-Side Rendering (SSR) رندر می‌شوند تا ربات‌های ردیاب بلافاصله مارک‌داون، متاتگ‌های سئو و داده‌های ساختاریافته (JSON-LD) را دریافت کنند. 

آسترو به‌صورت پیش‌فرض هیچ کُد جاوااسکریپتی به مرورگر کاربر نمی‌فرستد. بخش‌های تعاملی مثل باکس جستجوی زنده، ویجت لایک و منوی موبایل با کامپوننت‌های SolidJS پیاده‌سازی شده‌اند و فقط هنگام نیاز (`client:visible` یا `client:idle`) هیدراته می‌شوند. همچنین برای مقالاتی که تصویر شاخص آن‌ها ویدیو است، منطق رندر فرانت‌اند طوری تنظیم شده که به‌جای تگ `<img>` از `<video autoplay loop muted playsinline>` استفاده کند.

### ۲. نحوه ارتباط فرانت‌اند با سرویس‌های بک‌اند

فرانت‌اند درون کانتینر داکر قرار دارد و با دو سرویس بک‌اند صحبت می‌کند:

- **ارتباط با Django REST API:** آسترو هنگام رندر روی سرور، داده‌های مقاله و دسته‌بندی‌ها را مستقیماً از طریق شبکه داخلی داکر (`http://django-backend:8000/api/v1/`) می‌خواند. این کار تاخیر شبکه را به زیر ۵ میلی‌ثانیه می‌رساند.
- **ارتباط با FastAPI & TurboVec:** برای «مقالات مرتبط» در انتهای هر خبر، آسترو بردار ۷۶۸ بعدی مقاله را به سرویس FastAPI (`http://fastapi-turbovec:8001/api/search`) می‌فرستد تا ۳ مقاله شبیه به خبر جاری بازگردانده شوند.

برای جلوگیری از هاردکد شدن متغیرهای محیطی در زمان بیلد آسترو (`npm run build`) که باعث خطای ۵۰۰ در داکر می‌شد، متدی پیاده‌سازی شد که آدرس APIها را در زمان اجرا (Runtime) از `globalThis` می‌خواند:

```typescript
// lib/config.ts
export const getApiUrl = (): string => {
  if (typeof process !== 'undefined' && process.env.INTERNAL_DJANGO_URL) {
    return process.env.INTERNAL_DJANGO_URL; // فراخوانی درون‌شبکه‌ای داکر روی سرور
  }
  return 'https://teknovia.ir/api/v1'; // فراخوانی سمت کلاینت
};
```

### ۳. استراتژی کشینگ شبکه (Nginx + Cloudflare CDN)

برای کنترل بار سرور روی آسترو، کشینگ سه‌لایه پیاده‌سازی شده است:

1. **هدرهای پاسخ آسترو:** هدر `Cache-Control: public, max-age=0, s-maxage=300, stale-while-revalidate=600` تنظیم شده تا مرورگر صفحه را کش نکند اما CDN لبه تا ۵ دقیقه خروجی HTML را ذخیره کند.
2. **پروکسی معکوس Nginx:** درخواست‌های `/api/` و `/admin/` به جنگو هدایت می‌شوند و فایل‌های استاتیک و رسانه‌ها مستقیماً با کش ۳۰ روزه سرو می‌شوند.
3. **قواعد کش کلودفلر (Cache Rules):** با تنظیم شرط احترام به `s-maxage` در کلودفلر، اولین درخواست رندر شده و ۵ دقیقه در Edge ذخیره می‌شود. درخواست‌های بعدی از نزدیک‌ترین دیتاسنتر پاسخ داده می‌شوند.

هنگام انتشار خبر جدید، سیگنال جنگو متد Purge ای‌پیاآی کلودفلر را فراخوانی می‌کند تا کش به لحظه پاک شود:

```python
# services/cdn.py
import requests
from django.conf import settings

def purge_post_cache(slug: str):
    """ابطال فوری کش صفحه مقاله و صفحه اصلی در کلودفلر"""
    url = f"https://api.cloudflare.com/client/v4/zones/{settings.CF_ZONE_ID}/purge_cache"
    headers = {"Authorization": f"Bearer {settings.CF_API_TOKEN}", "Content-Type": "application/json"}
    data = {
        "files": [
            f"https://teknovia.ir/post/{slug}/",
            "https://teknovia.ir/"
        ]
    }
    requests.post(url, json=data, headers=headers, timeout=5)
```

## تکنولوژی‌های استفاده‌شده

- **بک‌اند:** Python 3.13, Django 6.0, Celery 5.6, Redis 7, Telethon
- **موتور برداری:** FastAPI + TurboVec (ابعاد ۷۶۸)
- **فرانت‌اند:** Astro 7.0, SolidJS, Tailwind CSS v4
- **پایگاه داده:** PostgreSQL 18
- **مدل‌های هوش مصنوعی:** DeepSeek-V4 Pro/Flash, Google Gemini 3.5 Flash & Embedding 2, deAPI (Qwen NF4 & ZImage), Pollinations AI (FLUX)
- **زیرساخت:** Docker Compose (۷ کانتینر)، Nginx، Cloudflare CDN

## راه اندازی سریع

```bash
# کلون پروژه
git clone https://github.com/Mj241084/teknovia-multi-agent-system
cd /var/www/teknovia

# بیلد و اجرای کانتینرها
docker compose up -d --build

# مایگریشن و جمع‌آوری استاتیک‌ها
docker compose exec django-backend python manage.py migrate
docker compose exec django-backend python manage.py collectstatic --noinput

# ریلود Nginx
nginx -t && systemctl reload nginx
```
